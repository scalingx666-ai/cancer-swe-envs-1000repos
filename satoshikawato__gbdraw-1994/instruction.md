# Issue

**Title:** Install a slot's Legend colors with its inventory, and type the editor state History restores

## Description

An artifact slot (the generated artifact a drawing keeps while another drawing is shown) now holds its set's generated Legend inventory and colors together, as `legend`, and installing the slot installs both through `installShownSetLegend`, the one install every Session Load, Load rollback and History restore already uses. Before, the colors were one of the slot's values and `installArtifactSlot` wrote them directly, but nothing installed the slot's inventory: `adoptShownSetInventory` kept the inventory already shown, filtered by the arriving set's Results. So during a switch the departing drawing's inventory stood next to the arriving drawing's colors until the binder adopted the arriving Result's inventory, and a Load that opens on a set other than the committed one left the committed set's inventory (written by `applyEditorArtifactData`) next to the opening slot's colors. Now the inventory and colors agree at every point of a switch and a Load; the state after the binder runs, and so the figure, is unchanged. This PR also types the editor state that History captures and restores (`EditorStateData`), so tsc now checks the restored Legend against `ShownSetLegend`. Session bytes and History steps are unchanged.

## Boundary analysis

- Channel: the shown set's generated Legend inventory and colors (`state.originalLegendOrder`, `state.originalLegendColors`). Writers: `installShownSetLegend` (slot install, Session Load, Load rollback, History restore) and the Legend owner after a draw or a records move. Readers: the Legend editor, Sort Default, Restore of deleted rows, the Generate request, Save (through its artifact views) and History capture. Key: the drawing's slot by `DrawingId`; the per-Result inventory the Legend owner keeps by Result identity.
- Rules applied: one owner per transformation (the colors and inventory have one install, `installShownSetLegend`; the second install in `installArtifactSlot` and the Legend owner's `adoptShownSetInventory` are removed); a value with one meaning per type (an empty slot is a slot, not `null`); typed boundaries (the slot's `legend`, Save's artifact view, History's editor capture and restore ports, `applyEditorArtifactData`; one explicit `any` fewer in `services/config.js`, no casts).
- Removed: the `originalLegendColors` slot key and its direct write; `writeShownSetInventory`; `adoptShownSetInventory` and its port; the `normalized` option of `applyEditorStateData`; the `null` slot install.
- Twin left: the generated artifact handle builds its editor state beside `buildEditorStateData` (both read the Legend paint and the shown set's Legend); the handle keeps the receipt and catalog in its owner set. Both now produce the one typedef; folding them into one capture is remaining work.
- Remaining work: `applyDrawingEditorData` keeps `Record<string, any>`, because Load's Legend row reader (`normalizeSessionLegendEntries`) returns untyped rows, not `LegendEntry`; typing it needs that reader to produce `LegendEntry`. The R11 bullet of `gbdraw/web/CLAUDE.md` still cites `applyEditorStateData(..., { normalized: true })`; the rule holds (a restore installs a copy as captured), and the citation changes in a rule-text PR, since rule text cannot change beside runtime files.

## Decisions taken alone

Owner-delegated (standing instruction 2026-09-29, restated 2026-10-07):

- The typed difference between "empty slot" and "the set a Load installed" is a real empty slot for the first and no call for the second, rather than a tagged union. Rejected: a `{ kind: 'empty' } | { kind: 'restored' }` argument to the hand-off, which keeps a branch the empty slot does not need.
- The slot install installs the arriving set's own inventory at once (through `installShownSetLegend`). This changes behaviour between the install and the binder's adopt: on `dev`, `installArtifactSlot` never wrote `originalLegendOrder`, and `adoptShownSetInventory` rewrote the inventory already shown, filtered by the arriving set's Results, so the departing drawing's inventory (on a switch) or the committed set's (on a Load opening on another set) stood next to the arriving colors. Now the inventory and colors agree at every point; the end state after the binder runs is unchanged, and the Legend owner still keeps each Result's inventory for the binder. Rejected: keeping the adopt port, which kept the mismatch and is a second writer of the inventory.
- `applyEditorStateData` lost its normalizing path, which only tests used; those tests pass a captured state. Rejected: keeping `normalized`, which forces the parameter to stay `unknown`.
